# RAG-20261109-001-DECISION-01：评测使用隔离 Chroma 副本与统一候选预算

- 日期：2026-11-09（Australia/Sydney）
- 状态：已采用
- 关联任务：[RAG-20261109-001](../execution_logs/RAG-20261109-001.md)

## 背景

需要在不修改生产 Chroma Collection、`.index_state/` 或原始 PDF 的前提下，对同一数据集和同一索引快照比较 Dense、BM25、Hybrid/RRF、Hybrid/RRF+Reranker。旧评测脚本只覆盖 Vector/Hybrid/Reranker，缺少 BM25-only、多证据 Recall、逐题候选和可复现元数据；且直接使用 `PersistentClient` 打开生产库可能触发磁盘写入。

## 候选方案

1. **直接用生产 `chroma_db/` 运行 `PersistentClient`**：实现最省事，但可能写 SQLite/HNSW 元数据，不符合只读验收要求。
2. **只用 SQLite 读取元数据，不运行向量检索**：完全不写库，但无法真实比较 Dense/Reranker，不能满足评测目标。
3. **把 `chroma_db/` 复制到临时目录，再把检索模块指向副本**：能运行完整四路检索，生产库只读；代价是临时磁盘和复制时间。
4. **从 PDF 重建临时索引**：最干净，但会重新计算 Embedding，且不能保证与当前生产快照完全一致，不适合作为“当前基线”。

## 决策

采用方案 3：

- `eval/run_cnooc_eval.py` 先把 `chroma_db/` 复制到 `tempfile.mkdtemp()`，再设置 `retrieval.DB_PATH` 指向副本，并清空模块级 `_collection`、BM25 corpus 缓存。
- 所有方法使用同一数据集、同一副本、候选预算 10；RRF k=60；BM25 使用 jieba；每个方法先用同一问题预热一次，再计时。
- 评测不调用 LLM；无答案题单独分组，不进入有答案检索指标分母。
- Reranker 的“关闭”对照通过独立 `retrieve_hybrid` 路径完成；没有为 API/CLI 增加运行时开关，避免扩大 P0 范围。

## 影响与验证

- 生产 `chroma_db/` 评测前后目录哈希一致：`c45504a26cec0942637c4a3da6c0544699fea32f048af2f86ec97d525dc9d44f`。
- 干净 venv + 隔离副本复跑得到相同四路指标，见 [评测报告](../../../reports/eval/cnooc_retrieval_eval_v1.md)。
- 限制：每次评测需要复制索引；模型必须本机已缓存或可下载；不同机器的延迟不可直接比较。
