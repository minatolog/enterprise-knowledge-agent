# DevLog #002 — RAG 小样本评测局限性与知识库规模扩展计划

**日期：** 2026-10-23  
**项目：** Enterprise Knowledge Agent  
**涉及模块：** Knowledge Base / Retrieval / Reranker / Evaluation  
**状态：** 问题分析完成，数据扩展与验证待实施

## 1. 背景（Background）

在前一阶段的 RAG 检索优化中，系统逐步实现了以下架构：

`Vector Search + BM25 → RRF Fusion → Cross-Encoder Reranker`

通过对同一组测试问题进行比较，观察到：

| Metric | Vector-only | Hybrid Search | Hybrid + Reranker |
|---|---:|---:|---:|
| Hit@1 | 83.33% | 83.33% | 100.00% |
| Hit@3 | 100.00% | 100.00% | 100.00% |
| MRR@3 | 0.9167 | 0.9167 | 1.0000 |

Reranker 成功改善了此前“输错十次密码”问题的错误排序。

然而，在进一步分析测试条件时，发现当前知识库规模很小，仅包含约 4 份企业制度文档和 10 个 Chunk，检索排序评测也只有 6 条有标准来源的问题。

因此，虽然当前实验取得了明显提升，但这些结果尚不足以证明算法在真实企业知识库中的泛化能力。

## 2. 发现的问题（Problem Identification）

### 2.1 知识库规模过小

当前候选文档数量有限，大部分测试问题都能够直接对应到某一个明确章节。

这种环境难以充分测试：

- 大量语义相似文档之间的检索竞争
- 不同部门制度之间的内容冲突
- 历史版本与当前有效版本的区分
- 长文档、多章节与跨文档推理
- 知识库规模扩大后的检索效率

因此，现有测试更接近功能验证，而非真实生产环境评估。

### 2.2 小样本评测结果存在局限

当前 Hit@1 = 100% 只表示 6 条测试问题全部正确命中第一名。

少量样本难以覆盖真实用户的多样化提问方式，也无法可靠估计系统面对未知问题时的表现。

此外，反复依据同一批测试题优化检索策略，可能使实验结果逐渐适应该测试集，产生评测过拟合风险。

### 2.3 Relevance 不等于 Answerability

在拒答阈值实验中发现：

问题：“输错密码会被永久封号吗？”

Reranker Score：`0.900418`

虽然文档包含密码错误与账号锁定规则，但并未充分说明永久封号制度。

这一结果说明：

**检索模型能够判断问题与文档是否相关，但高相关性分数并不能证明文档足以回答问题。**

单纯依赖检索分数设置拒答阈值，仍然可能放行缺乏证据支持的问题。

## 3. 问题分析（Root Cause Analysis）

目前认为主要存在三个限制。

**第一，Knowledge Coverage。**

检索算法只能利用知识库中实际存在的信息，不能弥补缺失的业务规则。

**第二，Retrieval Generalization。**

当前数据集缺少足够多的相似文档、干扰文档、长文档和跨文档场景，无法充分检验混合检索与 Reranker 的泛化能力。

**第三，Evaluation Design。**

现有评测集规模过小，并且部分问题已被反复用于检索策略优化，需要进一步建立独立测试集，避免对少量样本过度优化。

## 4. 解决方案（Proposed Improvements）

### 4.1 扩大企业知识库

计划分阶段构建更丰富的模拟企业知识文档，覆盖 HR、IT、安全、财务、差旅和内部运营等业务领域。

不仅增加文档数量，还将有意识地加入：

- 不同制度间的相似内容
- 历史版本和当前版本
- 精确数字、日期与业务规则
- 跨文档关联信息
- 缺少答案的边界问题

所有模拟文档将明确标识为 Synthetic Data，避免与真实企业资料混淆。

### 4.2 扩展检索评测数据集

将测试问题从少量基础问答扩展为覆盖以下场景的结构化数据集：

- Direct Fact Retrieval
- Semantic Paraphrase
- Exact Keyword / Number Matching
- Multi-document Retrieval
- Hard Negative Retrieval
- Unanswerable Questions

为每条问题标记标准来源、知识点和可回答性。

### 4.3 建立独立评测机制

区分用于选择阈值、调整检索策略的数据，与最终独立验证的数据。

使用相同的测试集对 Vector-only、Hybrid Search 和 Hybrid + Reranker 进行公平比较。

重点观察：

- Hit@1 / Hit@K
- MRR@K
- Recall@K（适用于多相关证据标注）
- False Rejection Rate
- False Acceptance Rate
- 查询延迟

### 4.4 引入 Evidence Sufficiency Evaluation

在相关性评估之外，增加证据充分性判断。

重点区分：

1. 文档包含明确答案。
2. 文档相关，但信息不足。
3. 文档完全无关。
4. 需要多个文档共同支持答案。

避免将 Reranker Score 直接当作答案正确率或充分证据的证明。

## 5. 下一阶段计划（Next Steps）

- [ ] 扩充多领域企业模拟知识库
- [ ] 构建包含难负例的评测问题集
- [ ] 建立校准集与独立测试集
- [ ] 对三种检索方案重新进行基线评测
- [ ] 分析知识库扩展后排名及拒答表现的变化
- [ ] 验证 Evidence Sufficiency 判断机制
- [ ] 记录优化前后指标与系统延迟

## 6. 阶段性结论（Conclusion）

本阶段认识到，RAG 系统的可靠性不能仅通过少量问答示例或高检索得分来证明。

更合理的工程实践应当基于具有代表性的知识库、困难样本和可复现的评测体系，区分检索相关性、答案可回答性以及最终生成质量。

**当前的 Hit@1 = 100% 是一次小样本实验结果，而不是系统已经达到生产级准确率的证明。**

下一阶段将以扩大知识库和改进评测设计为重点，通过更加真实的测试环境验证检索算法的实际价值。
